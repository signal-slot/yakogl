What runs today

OpenGL ES 2.0 runs on three boards under Zephyr. Four more boards are in progress.

The tests are the Khronos dEQP-GLES2 suite, run by us on each board. YakoGL has not been through the Khronos Adopters Program and is not a certified conformant implementation. The cases outside the pass count are not-supported cases and warnings; the records list them.

A board becomes supported when it boots from its own storage, passes the whole dEQP-GLES2 suite with 0 failures, and has its benchmarks recorded the same way. Support criteria.

Not yet

  • OpenGL ES 3.0. In development. Product builds report ES 2.0 by default. ES 3.0 record.
  • Speed in heavy scenes. Heavy benchmark scenes are slow, and the i.MX8MP's panel synchronization limits many lighter scenes. Measure your own UI.
  • Visual review. Every benchmark picture has recorded values. The Pi 4 and i.MX8MP pictures have not been reviewed by eye yet, and one i.MX8MP picture change is unexplained.
  • Repeated runs on the i.MX8MP. Earlier repeated boots showed intermittent failures in two regression cases. The latest run passes; the record does not show them fixed.
  • Touch input. The demos run without it.

Reading the records

  • dEQP-GLES2: the ES 2.0 mustpass list contains 17,165 cases. The i.MX8MP row counts 206 further cases outside that list. Not supported includes optional features and multisample cases a 1x surface cannot run. The AM62P row combines its 1x run with the 16 multisample cases from the older 4x image.
  • gl_test: YakoGL's regression cases read their results back from the GPU. The set differs by board. A passing run does not erase intermittent failures noted in the record.
  • glmark2-es2: 800×600, on-screen, all 33 scenes. Scores are benchmark results, not a promised application frame rate. The public Linux reference rows use different configurations; they are context rather than a controlled driver comparison.
  • Boot: the recorded tests load Zephyr from the board's own storage. Permanent-default boot modes and measured power-on latency are separate questions; see the boot record.
  • Builds: each result names its measurement date and build. The latest runs use different builds. A pre-publication build belongs to the earlier development repository; its hash is an identifier, and the public record is linked directly. A missing build commit is marked unverified.

The roadmap sets the project direction. The board record contains the measurement details and qualifications.
