What runs today

Three GPU families running on Zephyr. Here are the recorded results, the conditions behind them, and the work still in progress.

OpenGL ES 2.0: zero test failures on all three boards. These are our own runs of the Khronos dEQP-GLES2 test suite on real hardware. YakoGL has not been through the Khronos Adopters Program and is not a certified conformant implementation. Not-supported cases and warnings remain visible below.

Reading the results

  • dEQP-GLES2: the ES 2.0 mustpass list contains 17,165 cases. The latest AM62P and i.MX8MP runs also include 206 cases outside that list. Not supported includes optional features and multisample cases a 1x surface cannot run. The AM62P's separate 4x result comes from an older build; it is not added to the new 1x row.
  • gl_test: YakoGL's regression cases read their results back from the GPU. The set differs by board. A passing run does not erase intermittent failures noted in the record.
  • glmark2-es2: 800×600, on-screen, all 33 scenes. Scores are benchmark results, not a promised application frame rate. The public Linux reference rows use different configurations; they are context rather than a controlled driver comparison.
  • Boot: the recorded tests load Zephyr from the board's own storage. Permanent-default boot modes and measured power-on latency are separate questions; see the boot record.

In development

OpenGL ES 3.0

Product builds report ES 2.0 by default. The AM62P full-tree baseline is shown above; later targeted reruns improve individual groups, but do not constitute a new complete result. The Pi 4 has partial hardware results, with failures still present. The i.MX8MP has not run dEQP-GLES3 on the board yet; its host capability work is recorded separately from hardware validation. Read the ES 3.0 record.

Mali-G610 / NanoPC-T6 WIP

The fourth GPU back end is actively being brought up on the FriendlyElec NanoPC-T6 (Rockchip RK3588, Arm Mali-G610). The gpu-mali back end already runs gl_test on the board's Linux through the panthor kernel driver; the 2026-11-07 sweep records 147 of 256 cases PASS and 2 FAIL (a second color attachment, and 3D texture levels); of the others, 15 are refused, 83 not present and 9 skipped. Zephyr board support, board glue and GPU bring-up probes are already in the tree. Under Zephyr, an image started by kexec has powered the GPU on and read its ID (2026-10-19); the MMU and firmware steps are written on the host side and have not run on the board yet. The complete Zephyr graphics path and board-level validation are still in progress. This is therefore a WIP target, not yet one of the three supported Zephyr boards. Mali bring-up details · support criteria.

Armadillo-X2 WIP

The Atmark Techno Armadillo-X2 carries the same SoC and GPU as the Verdin iMX8M Plus (NXP i.MX 8M Plus, Vivante GC7000UL), so the gpu-vivante back end runs on it unchanged. It is a second development board for that back end: the Zephyr board files and the board runner are in the tree, and Zephyr images reach the board by kexec from its own Linux. Those are development runs, never results. Booting YakoGL from the board's own loader, with no Linux in between, is designed with host tests and has not run on the board. No dEQP or benchmark result exists for it yet. Direct-boot design · board runner notes.

STM32MP257F-DK WIP

The STMicroelectronics STM32MP257F-DK (two Cortex-A35 cores plus a Cortex-M33) has a smaller Vivante GPU, the GCNANOULTRA31. The port started when the board arrived in November 2026. In the tree: a pre-study of the hardware and of ST's open-source stack, the Zephyr board files, the C ABI over OP-TEE's watchdog and PSCI reset, a GPU identity probe tested against a host model, and a runner that boots one image from the board's own U-Boot and returns to ST's Linux. The first run of a YakoGL image on the board is the next step; nothing has rendered on it yet. Pre-study.

Raspberry Pi 5 WIP

The Raspberry Pi 5 (Broadcom BCM2712) has a V3D 7.1, a newer generation than the Pi 4's V3D 4.2. The V3D back end's 7.1 frame path (the clear-only frame and the frame checker) is built and run against a simulator on the host. For the board, a pre-study, the hardware facts read from Linux, and the first probe images (watchdog, boot, device tree, GPU identity, a clear-only frame) are in the tree, built and not yet run on the board. No GL result exists for it yet. Pre-study · V3D 7.1 facts · probes.

What to assess before integration

  • Your UI's performance. Heavy benchmark scenes remain slow, and the i.MX8MP's panel synchronization limits many lighter scenes. Measure your own application and display configuration.
  • Visual validation. Every benchmark scene has picture values recorded. Pi 4 and i.MX8MP results still need visual review; an i.MX8MP texture/mipmap picture change is unexplained. The records distinguish camera inspection from numerical comparisons.
  • Input and reliability. The demos currently run without touch input. The i.MX8MP regression record includes intermittent failures, even though its latest listed run passes the cases executed.

The roadmap sets the project direction. The board record contains the measurement details and qualifications.
