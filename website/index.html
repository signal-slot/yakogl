OpenGL ES 2.0 on embedded GPUs, with no GPU driver underneath

YakoGL is an OpenGL ES 2.0 and EGL library that drives the GPU of an embedded processor itself. An application written against the standard Khronos headers links one static library and draws on the real GPU from Zephyr: no Linux, no vendor driver stack, no software renderer. The same application source runs on three boards with three different GPUs.

What it is

A GPU normally sits behind a large driver stack in a full operating system. YakoGL puts that work in the library: it boots the GPU (and its firmware, on the PowerVR), sets up GPU memory, compiles shaders, builds the command streams and handles completion. The GL core and the three GPU back ends are one no_std Rust crate with a C ABI (libyakogl.a), so C, C++ and Rust applications link it alike. The GPU and display drivers it needs live in the same repository. Applications are ordinary GL ES 2.0 clients: glmark2 and the Khronos conformance tests run on it, and so does the Slint UI toolkit with FemtoVG, built no_std from upstream plus a patch kept in the repository.

Who it is for

  • Product teams building an instrument cluster, an HMI panel or another fixed-function display on an application processor with a GPU, who want a GPU-drawn UI on a real-time OS without bringing up Linux for it.
  • GPU and driver engineers who want a small, readable OpenGL ES stack: a Rust GL core tested on the host against a mock platform, three back ends side by side, and conformance results recorded per board and commit.
  • Board and SoC vendors who need OpenGL ES on a part where the vendor driver exists only for Linux.

Architecture

Five layers, from the application down. Only the shader back end and the OS abstraction are pluggable; everything above the OS abstraction is portable Rust.

Shader compilers and precompiled shaders

A GL application hands the library GLSL source at run time, so an ES 2.0 stack needs a shader compiler. YakoGL has its own: a no_std, allocation-free GLSL ES compiler (lexer, preprocessor, parser, semantic checks, an IR, and one back end per GPU) that runs on the board. Where a shader's machine code comes from is chosen when the image is built:

  • The compiler only (the default): any shader, compiled when the application asks.
  • Precompiled shaders in front of the compiler: the application's known shaders are compiled by the same compiler while the image is built; a hit runs no compile, a miss compiles.
  • Precompiled shaders only: no compiler and no scratch memory in the image; a shader the table lacks is refused by name.

The trade-off is measured, not assumed. On the AM62P the compiler costs bytes of flash plus about 5.2 MB of RAM for its working memory; a precompiled table for one test application costs bytes of flash and grows with the application's shader set. So precompiled shaders are an option for an image that wants no compiler, not the default.

Mesa's compilers (pco for PowerVR, etnaviv for Vivante) are the reference our output is compared against in host tests; a Zephyr or CMake product image links no Mesa-built shader table. Two small sets of the PowerVR driver's own programs (the end-of-tile programs and the boot self-test's vertex shader) are still Mesa's pco output; replacing them is open work.

Conformance and benchmarks

dEQP-GLES2: failures in the last whole tree

The Khronos conformance tests for OpenGL ES 2.0, the 17,165 cases of the mustpass list, run on Zephyr on the real GPU.

Read the AM62P tile with its history. The 54 failures of the 2026-10-10 tree are 9 shaders.invariance cases (fixed in e17fb6a7, image 1 passes 1,379 / 0 on it) and 45 vertex-texture cases (fixed on the host, board confirmation pending); the previous tree, on 2026-10-02, had none. The i.MX8MP tree is identical to the one of 2026-10-01. The Pi 4 was not run again: its 25 cube-map fixes are proved on the host only. Details on the status page.

glmark2-es2, 800x600 on-screen

All 33 scenes run on every board, but some still draw wrong, and performance work has not started. A public score for the same board under Linux with the vendor or Mesa driver is on the status page; the conditions differ, so read it as a direction, not a contest.

OpenGL ES 3.0

ES 3.0 is work in progress on the host: transform feedback state, uniform blocks, sized and integer formats are built in the GL core, but no back end renders them yet. Product builds (Zephyr, CMake) report ES 2.0 by default. The one dEQP-GLES3 board run so far, on the AM62P: of 42,810 ().

Getting started

On a board. Try it walks through the west workspace, the build and booting the Slint demo from the board's own storage.

On a PC, no board. The GL core and a back end run against a mock platform that models non-coherent GPU memory and flags unflushed, freed or out-of-range reads. With Rust 1.88 or newer and a C compiler:

git clone https://github.com/signal-slot/yakogl
cd yakogl
cargo test --no-default-features --features host-test,gpu-powervr
# the shader compiler, too
cargo test --no-default-features --features host-test,gpu-powervr,shaderc-online

Swap gpu-powervr for gpu-vivante or gpu-v3d. Exactly one GPU feature per build; none or two is a compile error.

Roadmap

The goals, in order, from HANDOFF:

  1. ES 2.0 finished on the three boards, each booted from its own storage. The known dEQP-GLES2 failures are fixed on the host; the AM62P invariance regression is fixed on main (e17fb6a7) and confirmed on the board. One confirming board session per board remains.
  2. Minimum performance. Not started; the benchmarks are first made to draw correctly.
  3. This website, live when the repository is public.
  4. OpenGL ES 3.0 on the three boards (the 42,810-case dEQP-GLES3 mustpass), host first.
  5. OpenGL ES 3.1 / 3.2 (#19).

Not yet planned in HANDOFF: touch input. Every demo today runs by itself.
