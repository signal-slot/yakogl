OpenGL ES,
no driver
underneath.

YakoGL is an OpenGL ES 2.0 and EGL library that drives the GPU of an embedded processor itself. An application written against the standard Khronos headers links one static library and draws on the real GPU from Zephyr: no Linux, no vendor driver stack, no software renderer.

What
it is

The driver's work, in the library.

A GPU normally sits behind a large driver stack in a full operating system. YakoGL puts that work in the library. The GPU and display drivers it needs live in the same repository.

  1. 01

    Boot

    It brings up the GPU itself.

    Power, clocks, GPU memory and, on the PowerVR, the firmware; then command streams and completion. No kernel driver in between.

  2. 02

    Compile

    Its own GLSL ES compiler, on the board.

    A no_std, allocation-free compiler with one back end per GPU, or a precompiled table, or both. How to choose.

  3. 03

    Link

    One source, three GPUs.

    The GL core and the three back ends are one no_std Rust crate with a C ABI (libyakogl.a). C, C++ and Rust applications link it alike: glmark2, the Khronos conformance tests and the Slint UI toolkit run on it.

Who
it is for

Product teams

Building an instrument cluster, an HMI panel or another fixed-function display on an application processor with a GPU, and wanting a GPU-drawn UI on a real-time OS without bringing up Linux for it.

GPU and driver engineers

Wanting a small, readable OpenGL ES stack: a Rust GL core tested on the host against a mock platform, three back ends side by side, dEQP results recorded per board and commit.

Board and SoC vendors

Needing OpenGL ES on a part where the vendor driver exists only for Linux.

dEQP-GLES2

dEQP-GLES2: failures in the whole tree

The Khronos conformance tests for OpenGL ES 2.0, the 17,165 cases of the mustpass list, run on Zephyr on the real GPU. Each board ran the whole tree from main e9901869a (2026-10-15/16), booted by its own bootloader. The cases counted as not supported are features ES 2.0 does not have, or the multisample cases a 1x configuration cannot run (the AM62P runs those on a 4x image, and they pass).

glmark2-es2, 800x600 on-screen

All 33 scenes run on every board with no failed scene and no GL error. Each scene's picture is recorded and checked on the AM62P (on its panel); the Pi 4 and the i.MX8MP are next. The slow scenes (terrain, shadow, refract) are where performance work goes first. A public score for the same board under Linux with the vendor or Mesa driver is on the status page; the conditions differ, so read it as a direction, not a contest.

OpenGL ES 3.0

ES 3.0 is built on the host for the three GPUs: transform feedback, uniform blocks, sized and integer formats, occlusion queries, glBlitFramebuffer, sRGB and buffer mapping. Product builds (Zephyr, CMake) report ES 2.0 by default. The whole dEQP-GLES3 tree has run on the AM62P (2026-10-14; two cases hang its GPU, and 998 cases have no result): of 42,810 (). The Pi 4 has run 7 of its 91 images; the i.MX8MP has not run it yet.

Five
layers

From the application down. Only the shader back end and the OS abstraction are pluggable; everything above the OS abstraction is portable Rust.

Shaders

Compiled on the board, before it, or both.

A GL application hands the library GLSL source at run time, so an ES 2.0 stack needs a shader compiler. YakoGL has its own: lexer, preprocessor, parser, semantic checks, an IR, and one back end per GPU. Where a shader's machine code comes from is chosen when the image is built.

  1. A

    The compiler only

    The default: any shader, compiled when the application asks.

  2. B

    Precompiled in front of the compiler

    The application's known shaders are compiled by the same compiler while the image is built; a hit runs no compile, a miss compiles.

  3. C

    Precompiled only

    No compiler and no scratch memory in the image; a shader the table lacks is refused by name.

The trade-off is measured, not assumed. On the AM62P the compiler costs bytes of flash plus about 5.2 MB of RAM for its working memory; a precompiled table for one test application costs bytes of flash and grows with the application's shader set. So precompiled shaders are an option for an image that wants no compiler, not the default.

Compiler:
Table:

Mesa's compilers (pco for PowerVR, etnaviv for Vivante) are the reference our output is compared against in host tests; a Zephyr or CMake product image links no Mesa-built shader table. Two small sets of the PowerVR driver's own programs (the end-of-tile programs and the boot self-test's vertex shader) are still Mesa's pco output; replacing them is open work.

Start.

On a board. Try it walks through the west workspace, the build and booting the Slint demo from the board's own storage.

On a PC, no board. The GL core and a back end run against a mock platform that models non-coherent GPU memory and flags unflushed, freed or out-of-range reads. With Rust 1.88 or newer and a C compiler. Swap gpu-powervr for gpu-vivante or gpu-v3d; exactly one GPU feature per build, none or two is a compile error.

$ git clone https://github.com/signal-slot/yakogl
$ cd yakogl
$ cargo test --no-default-features \
    --features host-test,gpu-powervr
# the shader compiler, too
$ cargo test --no-default-features \
    --features host-test,gpu-powervr,shaderc-online

Road
map

The goals, in order, from ROADMAP.

  1. Met

    ES 2.0 finished on the three boards

    Each booted from its own storage, with zero dEQP-GLES2 failures from one commit.

  2. Now

    Minimum performance

    glmark2-es2 runs its 33 scenes on every board with no failed scene and no GL error; each scene's picture is checked (done on the AM62P, next on the Pi 4 and the i.MX8MP) and its frame rate recorded. The demos (the Slint sample) are kept working on every board but are not benchmarks.

  3. Next

    Public release

    With this website, live when the repository is public.

  4. Then

    OpenGL ES 3.0

    On the three boards (the 42,810-case dEQP-GLES3 mustpass), host first.

  5. Then

    More boards

    Each joining when it meets stages 1 and 2.

Beyond the stages, not scheduled: OpenGL ES 3.1 / 3.2 (#19) and touch input (#24). Every demo today runs by itself.

The name.
