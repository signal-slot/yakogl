# Source form: upstream code in upstream form, our code in Rust

The rule (decided 2026-10-01):

1. Code brought in from elsewhere stays in its upstream form: vendored
   unmodified at a pinned version with its own licence files, our adaptations
   in separate files, generated files produced by the upstream's generators,
   so that it can be updated. The only exception is code whose licence does
   not allow bringing it in (GPL-only Linux drivers); it is replaced, or
   rewritten from documentation, and a rewrite is original code.
2. Everything original to the project is Rust; thin C only where Zephyr or
   Linux registration forces it.

This document maps each part of the tree to that form and says in which order
the work is done. `third_party/README.md` has the vendoring procedure,
`NOTICE` the origins as they stand today. It is based on a provenance audit
and a design study of origin/main at `db7a2085` (2026-10-01). No Linux source
tree was available to either; statements about Linux file licences below are
from our own file headers and are **not verified**.

## Group by group

**A. PowerVR firmware interface, MMU, boot** (`pvr_bringup.c`,
`pvr_fw_boot.c`, `pvr_fw_trace_decode.*`; `pvr_fwif.h` and
`pvr_rogue_fwif_sf.h` until step 2). The board runs the TI/Img DDK 25.2 firmware ABI
(`SAFEUI_GPU_PVR_DDK_FW` is the default), not mainline drm/imagination's.
`pvr_fwif.h` today is five mainline headers merged, with 10 `PVR_DDK_FW`
blocks bending it to the DDK; `pvr_fw_boot.c` mixes mainline MMU/FW/CCB code,
the DDK's `rgxstartstop.c` sequence and bring-up experiments. The DDK kernel
source is Dual MIT/GPLv2 (661 of 668 files under `include/`, `hwdefs/`,
`services/`), so it is the upstream. Target: vendor the DDK FWIF headers and
register definitions, and `rgxlayer.h` / `rgxfwimageutils.[ch]` /
`rgxstartstop.[ch]`, which the DDK wrote to be used outside the DDK; ours is
the implementation of `rgxlayer.h` plus the MMU, CCB and render service
written against the vendored types. The trace decoder uses the DDK's
`rgx_fwif_sf.h` (944 entries; the mainline table we carry has 779).
State (step 6, branch `form/6-rgxlayer`): the firmware start (`RGXStart`),
stop (`RGXStop`, wired as `pvr_fw_stop()`, not called yet) and image load
(`RGXGetFWImageAllocSize`, `RGXProcessFWImage`) are the DDK's, compiled
unmodified (`driver/compat/pvr_rgxstartstop.c`, `pvr_rgxfwimageutils.c`: the
environment of `pvr_ddk.h`, TEE_DDK, nothing else). `rgxlayer.h` is
implemented in Rust, `driver/rust/src/gpu/pvr/rgxlayer.rs` (33 functions
exported with the DDK's names and C signatures; `hPrivate` is
`struct yd_pvr_layer` of `yakogl_drivers.h`), except `RGXCommentLog` and
`RGXErrorLog`, which are C-variadic and so C (`driver/compat/pvr_rgxlayer_log.c`).
The core's answers (features, errata, feature values) come from the vendored
`rgxconfig_km_36.V.104.796.h` / `rgxcore_km_36.53.104.796.h`; the board's
build asserts the two words against them (`driver/compat/pvr_rgxlayer_check.c`
over the generated `pvr_rgx_core.h`) and the host check asks every one
(`tools/pvr/rgxlayer_check.c`). The META/MIPS entry points answer "not
supported". The DDK-derived sequences in `pvr_fw_boot.c` are deleted
(`pvr_fw_start`'s reset/SLC/ECC/RISC-V wrapper/AXI/BIF/DMACTIVE copy, the
remap values captured from a running DDK, the ELF/layout loader); what that

`dsb st` barriers; the two boot windows take the DDK's 32 MiB values; nine

image placement is byte-identical on the real firmware. Board (AM62P): the
handshake lines are identical, gl_triangle renders, dEQP fbo and
shaders.texture_functions 731/0/0/0.
State (step 7, branch `form/7-pvr-kernel-rust`): nothing of drm/imagination
is left. The kernel side is ours, in Rust against the vendored DDK types
(`driver/rust/src/gpu/pvr`; driver/docs/pvr-kernel-rust.md has the inventory
with each function's origin and fate): the carveout's allocators (`mem`), the
page tables on the `rgxmmudefs_km.h` formats (`mmu`), the KCCB/FWCCB and the

**The mechanism.** Code written for these drivers is one `no_std` Rust crate,
`yakogl-drivers` at `driver/rust/` (a workspace member; the path is named only
there and in `YAKOGL_DRIVERS_CRATE_DIR` in `driver/zephyr/CMakeLists.txt`),
with modules `ip::*` (one IP block each, SoC-independent), `soc::imx8mp::*` and
`soc::am62p::*`, cargo features `imx8mp` and `am62p`, and no dependencies. It
is built for `aarch64-unknown-none-softfloat` (it runs at PRE_KERNEL_1 and in
ISRs, where arm64 Zephyr forbids the FP registers) into
`libyakogl_drivers.a` by `yakogl_add_rust_archive()`
(`capi/yakogl_capi.cmake`, the generalised `yakogl_add_capi_archive()`), and
post-processed by `capi/assemble.cmake` with the crate's LTO member as a
parameter, so its Rust runtime and compiler_builtins' libc names are local
and it links beside `libyakogl.a` and an application's Rust staticlib. A
hidden `SAFEUI_DISPLAY_RUST`, selected by each Rust-backed driver, turns the
build on; the features follow the drivers enabled. Zephyr sees thin C shims
in `driver/drivers/<class>/`: `DEVICE_DT_INST_DEFINE` and the class's
`DEVICE_API`, `device_map()` of each register range, pinctrl, kernel objects
(locks, semaphores), `IRQ_CONNECT` to a C ISR that calls a Rust function
returning event bits. Devicetree values reach Rust as a `#[repr(C)]`
configuration in `dev->config`, mutable state as a `#[repr(C)]` blob in
`dev->data` (no Rust statics, so instances are independent); both layouts are
pinned on both sides (`driver/rust/include/yakogl_drivers.h`
`_Static_assert`s, Rust `offset_of!` asserts). Every OS service comes in as
`struct yd_env` (busy-wait, sleep, log, I2C, GPIO; `yd_env_init()` fills it
on Zephyr, the host tests their own), and registers are read and written
through an `Mmio` trait whose hardware form is Zephyr's arm64
`sys_read32`/`sys_write32` inline (`ldr w` + `dmb sy`, `dmb sy` + `str w`).
Register offsets and fields come from `soc/imx8mp/regs.rs`, generated from the
unmodified hal_nxp `PERI_*.h` (revision 1e91007b, sha256-pinned) by
`tools/hal-nxp/gen_regs.py`; `tools/check.sh` regenerates and compares. The
host tests (`cargo test -p yakogl-drivers`) run each driver against a register

## What cannot be brought to upstream form, and why

- **Driver-level orchestration.** Mesa's Gallium and Vulkan drivers
  (`v3dx_*`, `etnaviv_emit/state`, `pvr_clear/blit/arch_cmd_buffer/arch_job_*`)
  need the pipe or vk runtime. Our composition code stays ours, on generated
  packers.
- **The compiler core (F3).** Mesa's compilers are NIR/ralloc C and cannot be
  separated for a `no_std` target.
- **The DDK kernel server** (MMU/devicemem, CCB, render and firmware
  contexts): only by porting the DDK's environment layer to Zephyr (107
  `osfunc` functions plus physmem, sync and threads; about 170k lines to
  carry). That is a decision about size, not feasibility.
- **Mainline drm/imagination.** It needs DRM/GEM/drm_sched, and its firmware
  ABI is not the one the board runs.
- **GPL-only sources** (Linux display drivers, the etnaviv kernel driver, v3d,
  bcm2835-power): replaced or rewritten from documentation only.
- **V3D registers**: no permissive source exists; written in our own form (below).

## Decided: the V3D register file

Decided 2026-10-01 by the project owner. Mesa has no V3D register
definitions, and Broadcom published no V3D 4.x documentation, so there is no
permissive upstream to bring in. Hardware facts (offsets, bit positions, the
order the hardware needs things done in) are used; the names and the ordering
of the code are our own, taking Mesa's simulator glue names
(`v3d_regs.h`, src/broadcom/simulator) wherever Mesa has one. The Linux
citations are removed from `v3d_regs.h`, `v3d_hw.c` and
`src/osal/zephyr_v3d.c`.
