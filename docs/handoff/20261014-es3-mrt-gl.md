Base: integration tip `2769e77d`. Code: `src/backend.rs` (`DRAW_TARGETS`,
`draw_targets`, `HOST_DRAW_TARGETS`), `src/gl/context.rs`
(`CAP_COLOR_ATTACHMENTS` = 4, `max_draw_buffers()`, `max_color_attachments()`),

`a_four_target_back_end_is_handed_four_colour_attachments`,
`src/testutil.rs` `TestGl::backend_draws_targets`.

## State of main

No board number changes. Every back end still reports what it reported:
GL_MAX_DRAW_BUFFERS and GL_MAX_COLOR_ATTACHMENTS are 3 on the PowerVR, the
GC7000UL and the V3D, and the ES 2.0 report is unchanged.

## Open work

RC14 (`docs/es3-cts-failures.md`), GL-core half done:

- The draw-buffer count is now the back end's: `backend::DRAW_TARGETS`
  (3 for each GPU). GL_MAX_DRAW_BUFFERS, GL_MAX_COLOR_ATTACHMENTS,
  GL_DRAW_BUFFERi, glClearBuffer's draw-buffer range, every attachment-point
  check and the shader's `gl_MaxDrawBuffers` read it. A back end that draws
  fewer than 4 names no point past its count, so nothing is advertised that
  it cannot draw.
- The framebuffer object stores 4 colour points (`GL_CAP_COLOR_ATTACHMENTS`
  4; `struct gl_framebuffer` 92 -> 108 bytes, `struct gl_context` grows by
  4 KiB, so +8 KiB of `.bss` with the default 2 contexts).
- The draw already carried 4 slots (`GLES_MAX_TARGETS`); with a 4-target
  back end a draw and a clear hand it all 4 (host test, fake back end).
- glDrawBuffers: `GL_COLOR_ATTACHMENTm` is now an accepted value for any
  m below 32; m at or past GL_MAX_COLOR_ATTACHMENTS is
  GL_INVALID_OPERATION, as ES 3.0 4.2.1 and Mesa say. It was
  GL_INVALID_ENUM. No other error changed.

Left: the back-end half. Each GPU raises its own `DRAW_TARGETS` arm in
`src/backend.rs` to 4 once a board draws 4 targets. Then the queries, the
attachment points and `gl_MaxDrawBuffers` follow with no other change.

- **PowerVR (AM62P)**: the driver's end-of-tile programs and the kick's PBE
  words exist for 3 targets (`PVR_RENDER_MAX_RT` 3 in
  `driver/src/pvr_render.h`, `eot_doutu_src0_n[]`; `src/pvr/backend.rs`
  `PVR_BACKEND_MAX_RT` clamps `num_targets` to 3). A fourth needs its PBE
  state per render target (`docs/es3-pvr-formats.md` 1.2 and 2.5) and a
  fourth end-of-tile program. The USC has 4 output registers a pixel
  (`docs/es3-pvr-formats.md` 1.8) and the compiler writes 4 colour outputs
  (`select.rs` `MAX_COLOUR_OUTPUTS` 4).
- **V3D 4.2 (Pi 4)**: the TLB takes render targets 0-3, the compiler writes
  4 (`shaderc/online/v3d/prepare.rs` `MAX_RTS` 4), and the backend takes up
  to 4 attachments (`docs/online-shaderc/v3d-backend.md`, "Multiple render
  targets", step 4 pending). What is left is a board run that draws into
  target 3, then `DRAW_TARGETS` 4.
- **GC7000UL (i.MX8MP)**: the PE has 4 render targets (etnaviv `num_rts`,
  halved for 64-bit formats) and `vivante::backend::mrt_targets` takes up to
  4. Check that the shader back end writes a fourth output and that the PE
  programs RT 3, on the board, then `DRAW_TARGETS` 4. A 64-bit format on a
  target may halve the count: that would need a per-format check at
  framebuffer completeness, not a lower `DRAW_TARGETS`.

When a GPU's arm becomes 4, the unit tests that use GL_COLOR_ATTACHMENT3 as
"past the limit" are already written against `max_color_attachments()`;
`tests/es2_report_guard.rs` `draw_buffer_queries_are_invalid_enum` and
`tests/es3_caps.rs` (caps-land, not on main yet) pin 3 for
GL_MAX_COLOR_ATTACHMENTS and must move to 4 in the same change.

Not done here, found on the way:

  It passes there today (run by hand).
- The GL core has no check of a fragment output at a location at or past
  GL_MAX_DRAW_BUFFERS (`src/gl/program.rs`, `src/shaderc/online/sema.rs`);

  shader outputs) makes it a link error was not checked against the spec
  text for this note.
- glFramebufferTexture*/Renderbuffer and the attachment query answer
  GL_INVALID_ENUM for a colour point past the limit. Mesa answers
  GL_INVALID_OPERATION there (GL 4.5 9.2.8). ES 3.0's table only lists the
  points that exist, so both readings exist; unchanged here.
