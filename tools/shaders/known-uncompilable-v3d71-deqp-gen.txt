# Harvested dEQP-GLES2 programs (tools/cts/deqp-es2-programs.sh) that the 4.2
# back end compiles and the V3D 7.1 online back end refuses
# (tests/shaderc71_deqp_programs.rs). `<program id>: <exact message>`, the
# message being V3d71Error's Debug form. A refusal not listed, a changed
# message and a listed program that now compiles all fail the test.

# 7.1-only, harness: dEQP-GLES2.functional.attribute_location.bind_aliasing.
# max_cond_{float,vec2,vec3,vec4,mat2,mat3}. The limit hit is the 16 vertex
# attribute records of V3D (one per distinct attribute location the vertex
# shader reads, V3D's 16 vec4 attribute inputs). The check is
# src/shaderc/online/v3d/chain71.rs:521-522 (`records.len() > 16`, NotYet
# "more than 16 vertex attributes"); 4.2 has the same check and message at
# src/shaderc/online/v3d/chain.rs:517. `records` is built the same way in both
# (chain71.rs:507-518, chain.rs:503-514): the distinct `SOp::Attr` locations of
# the prepared vertex shader. The back ends do not differ; the inputs do. The
# case declares more than 16 attributes and aliases several to one location
# with glBindAttribLocation, so the GL run that made the 4.2 outcome in
# index.tsv had at most 16 distinct locations. The harvest keeps the shader
# text only, not the bindings, and compile_program71 gives every declared
# attribute its own location, so `records` exceeds 16 here. Refusing is
# right for that input (more than 16 distinct locations cannot be bound). Not
# a back-end defect; the bindings are not in index.tsv or programs/, so the
# harness cannot honour them.
