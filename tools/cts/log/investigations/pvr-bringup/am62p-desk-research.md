## 1. IMG BXS GPU, firmware, licences, Mesa

**GPU variant.** Toradex Verdin AM62P datasheet (https://docs.toradex.com/117145-verdin_am62p_datasheet.pdf, §1.4.2 Table 2): "GPU Model: PowerVR® BXS 4-64 MC1". TI kernel DT node (TIK k3-am62p-j722s-common-main.dtsi):
```
gpu: gpu@fd80000 {
	compatible = "ti,am62p-pvr", "img,pvr-bxs64";
	reg = <0x00 0x0fd80000 0x00 0x80000>;
	interrupts = <GIC_SPI 241 IRQ_TYPE_LEVEL_HIGH>;
	power-domains = <&k3_pds 237 TI_SCI_PD_EXCLUSIVE>, <&k3_pds 242 TI_SCI_PD_EXCLUSIVE>;
	assigned-clocks = <&k3_clks 237 3>; assigned-clock-rates = <800000000>;
```
TI's Processor SDK graphics build guide shows the BVNC read at runtime: "Read BVNC 36.53.104.796 from HW device registers" (https://software-dl.ti.com/processor-sdk-linux/esd/AM62PX/latest/exports/docs/linux/Foundational_Components/Graphics/Rogue/Build_Guide.html). Mainline binding `Documentation/devicetree/bindings/gpu/img,powervr-rogue.yaml` lists `ti,am62p-gpu` + `img,img-bxs-4-64` + `img,img-rogue` (https://github.com/torvalds/linux/blob/master/Documentation/devicetree/bindings/gpu/img,powervr-rogue.yaml). Mainline master `k3-am62p-j722s-common-main.dtsi` contains **no gpu, dss or dsi node** (grep of the downloaded file) — only the TI kernel has them.

**Firmware file names / where they live.**
- Upstream linux-firmware WHENCE (https://git.kernel.org/pub/scm/linux/kernel/git/firmware/linux-firmware.git/plain/WHENCE): "Driver: powervr - Imagination Technologies PowerVR graphics driver / File: powervr/rogue_33.15.11.3_v1.fw / File: powervr/rogue_36.52.104.182_v1.fw / File: powervr/rogue_36.53.104.796_v1.fw / Version: 1.1.OS@6976702 / License: Redistributable. See LICENSE.powervr for details". The mainline driver builds the name as `powervr/rogue_<B.V.N.C>_v1.fw` (drivers/gpu/drm/imagination/pvr_device.c, comment "e.g. powervr/rogue_4.40.2.51_v1.fw"). So for BXS-4-64 (36.53.104.796) the open-source stack uses `powervr/rogue_36.53.104.796_v1.fw` from linux-firmware.
- ti-linux-firmware (git.ti.com/processor-firmware/ti-linux-firmware, branch ti-linux-firmware) does **not** carry the BXS GPU firmware. Its `ti-img/` directory contains only `pvdec_full_bin.fw` (D5520 video decoder; GitHub API listing of https://github.com/TexasInstruments/ti-linux-firmware/tree/ti-linux-firmware/ti-img). `LICENSE.ti-img` there begins "This license applies to the Imagination D5520 firmware image, pvdec_full_bin.fw." (https://git.ti.com/cgit/processor-firmware/ti-linux-firmware/plain/LICENSE.ti-img?h=ti-linux-firmware).
- For TI's proprietary stack, the GPU firmware is inside the umlibs binaries: "All interactions with the GPU require the proprietary user space components. It has the actual firmware binaries, GLES / Vulkan / OpenCL implementation, and the primary control server." (Build_Guide above).

Limited patent license. …"

**"TI-TFL" (TI Text File License).** The umlibs `LICENSE` (https://git.ti.com/cgit/graphics/ti-img-rogue-umlibs/plain/LICENSE?h=linuxws/scarthgap/k6.12/25.2.6850647) is titled "TEXAS INSTRUMENTS TEXT FILE LICENSE" and says: "Redistribution and use in binary form, without modification, are permitted provided that the following conditions are met: * No reverse engineering, decompilation, or disassembly … * any redistribution and use are licensed by TI for use only with TI Devices. * Nothing shall obligate TI to provide you with source code …". The umlibs LICENSE also appends Khronos notices.

**Kernel driver (ti-img-rogue-driver).** Open source. README (https://git.ti.com/cgit/graphics/ti-img-rogue-driver/plain/README?h=linuxws/scarthgap/k6.12/25.2.6850647): "You may use, distribute and copy this software under the terms of the MIT license. Details … in the file 'MIT-COPYING'. Alternatively … GNU General Public License version 2 … 'GPL-COPYING'." TI's doc classifies it "(Open Source, but out-of-tree)". Branches seen: `linuxws/scarthgap/k6.6/24.1.6554834`, `linuxws/scarthgap/k6.12/24.2.6643903`, `linuxws/scarthgap/k6.12/25.2.6850647`, `linuxws/scarthgap/k6.18/25.3.6908880` (https://git.ti.com/cgit/graphics/ti-img-rogue-driver/refs/).

**User-mode libraries (ti-img-rogue-umlibs).** TI doc: "The GLES / Vulkan / OpenCL user mode (UM) libraries (Closed Source, binary release)"; layout `targetfs/am62p_linux/lws-generic/release`; licence = the TI Text File License quoted above. TI doc also states the open-source alternative: kernel "powervr" module "Available in the upstream linux repository as of version 6.8", firmware from linux-firmware, Mesa `-Dvulkan-drivers=imagination-experimental` (Build_Guide).

**Mesa `pvr` (src/imagination).** https://docs.mesa3d.org/drivers/powervr.html "The following hardware is currently in active development": AXE-1-16M 33.15.11.3 (Vulkan 1.2), BXM-4-64 36.52.104.182 / 36.56.104.183, **BXS-4-64 36.53.104.796 (Vulkan 1.2)**. "The driver is conformant to Vulkan 1.2 on BXM-4-64 (36.52.104.182) and BXS-4-64, but not yet on other GPUs" (others need `PVR_I_WANT_A_BROKEN_VULKAN_DRIVER=1`). Device-info files: `src/imagination/common/device_info/{axe-1-16m,bxe-2-32,bxe-4-32,bxm-4-64,bxs-4-64,g6110,ge7800,ge8300,gx6250,gx6650}.h` (https://gitlab.freedesktop.org/mesa/mesa/-/tree/main/src/imagination/common/device_info). Imagination: "AXE-1-16(M) and BXS-4-64 cores are supported with Linux kernel 6.16 and later"; "Conformant Vulkan 1.0 driver … available as part of Mesa 25.3" (https://developer.imaginationtech.com/solutions/open-source-gpu-driver/). The Mesa page does not name AM62P explicitly; the mainline DT binding does (`ti,am62p-gpu`).

## 2. Display: DSS0/DSS1, display sharing, DSI, Toradex DSI accessories

**DSS nodes (TIK k3-am62p-j722s-common-main.dtsi).**
- `dss0: dss@30200000 { compatible = "ti,am62p51-dss"; reg = common 0x30200000, vidl1 0x30202000, vid 0x30206000, ovr1 0x30207000, ovr2 0x30208000, vp1 0x3020a000 /* vp1: Used for OLDI */, vp2 0x3020b000 /* vp2: Used as DPI Out */, common1 0x30201000; interrupts = <GIC_SPI 84>; power-domains 186 (DSS0), 243 (OLDI0), 244 (OLDI1) }` with `oldi-transmitters { oldi0_dss0, oldi1_dss0 }`.
- `dss1: dss@30220000 { compatible = "ti,am62p52-dss"; reg = common 0x30220000, vidl1 0x30222000, vid 0x30226000, ovr1 0x30227000, ovr2 0x30228000, vp1 0x3022a000, vp2 0x3022b000, common1 0x30221000; interrupts = <GIC_SPI 30>; }`.
- Each DSS has two register "common" regions (common, common1) — this is what enables sharing.

**DSI controller and PHY (TIK).**
```
dphy_tx0: phy@301c0000 { compatible = "ti,j721e-dphy"; reg = <0x0 0x301c0000 0x0 0x1000>; clocks = <&k3_clks 238 16>, <&k3_clks 238 1>; assigned-clock-rates = <25000000>; }
dsi0: dsi@30500000 { compatible = "ti,j721e-dsi"; reg = <0x0 0x30500000 0x0 0x100000>, <0x0 0x30270000 0x0 0x100>;
	clocks = <&k3_clks 231 2>, <&k3_clks 231 5>; clock-names = "dsi_p_clk", "dsi_sys_clk"; power-domains = <&k3_pds 231 …>;
	interrupts = <GIC_SPI 86 IRQ_TYPE_LEVEL_HIGH>; phys = <&dphy_tx0>; }
```
(`ti,j721e-dsi` is the Cadence DSI wrapper driver `cdns-dsi-j721e`.) The DSI output is fed from **DSS1 VP1**: TI overlay `k3-am62p5-sk-dsi-rpi-7inch-panel.dtso` has `&dss1_ports { /* DSS1-VP1: DSI Output */ port@1 { dss1_dpi1_out → dsi0_in } }` (TIK). TI Linux DSS doc: "The OLDI output, configured as Dual-Link in the DT overlay, is sourced from DSS0, while the DSI output gets sourced from the DSS1" and "MIPI DSI: 4 Lane MIPI DSI output from the SoC directly" (https://software-dl.ti.com/processor-sdk-linux/esd/AM62PX/latest/exports/docs/linux/Foundational_Components/Kernel/Kernel_Drivers/Display/DSS7.html). Mainline master has none of these nodes (see §1).

**TI "display sharing" documentation.**
- MCU+ SDK DSS Display Share example (https://software-dl.ti.com/mcu-plus-sdk/esd/AM62PX/latest/exports/docs/api_guide_am62px/examples/drivers/dss_display_share.html): "Display subsystem supports sharing of display between multiple hosts as it provides separate register space (common* region) for each host … and also an unique interrupt line for each host. HLOS like Linux owns one or more of the video planes with video port (along with corresponding overlay manager) … being owned and controlled by a remote core." "The example uses DSS0 instance with VIDL pipeline, OVR1 overlay and VP1 videoport. The overlay manager is configured with Zorder 1 for VID pipeline and Zorder 2 for VIDL pipeline. The example acts as master for controlling DSS and expects linux to use VID pipeline." "The example configures OLDI LVDS panel for Video Port 1." Supported combination: "CPU + OS: **wkup-r5fss0-0 freertos**" (i.e. it runs on the DM/WKUP R5F, not the MCU R5F). It also programs firewalls: read-only access for Linux to DSS registers used by RTOS, and an RTOS-only framebuffer region. Linux overlays: `k3-am62p5-sk-microtips-mf101hie-panel.dtbo` and `k3-am62p5-sk-dss-shared-mode.dtbo`. Note: "As the wake-up R5 is the device manager, it needs to be started by the SBL."
- MCU+ SDK DSS driver (https://software-dl.ti.com/mcu-plus-sdk/esd/AM62PX/latest/exports/docs/api_guide_am62px/components/drivers/dss.html): supports "Video Pipleline configuration for VID and VIDL", "VP1 and VP2", "single link and dual link OLDI panel on VP1", "DPI configuration for VP2", and "display sharing with HLOS with VIDL pipeline, OVR1 and VP1 in control of MCU and zorder configuration controlled by MCU." Safety features: "4 programmable … safety check regions on each display output", "1 safety check region on each input video pipeline output", "MISR … freeze frame detection". **DSI is not listed** anywhere in the MCU+ SDK DSS driver features ("DSS supports two types of display interfaces: DPI via VP2 … LVDS via OLDITX0/1 connected to VP1").
- Linux side (https://software-dl.ti.com/processor-sdk-linux/esd/AM62PX/latest/exports/docs/linux/How_to_Guides/Target/How_to_enable_display_sharing_between_remotecore_and_Linux.html and DSS7 page): properties `ti,dss-shared-mode`, `ti,dss-shared-mode-planes`, `ti,dss-shared-mode-vp`, `ti,dss-shared-mode-vp-owned`, `ti,dss-shared-mode-common`, `ti,dss-shared-mode-plane-zorder`. Example A (Linux owns one plane): Linux = common1 / VP1 shared / Vid; remote = common / VP1 owned / Vidl. Example B (Linux owns a full pipeline): Linux VP1 owned + Vid, remote VP2 owned + Vidl. The overlay `k3-am62p5-sk-dss-shared-mode.dtso` (TIK) sets `interrupts = <GIC_SPI 85 …>` for Linux (the second DSS0 interrupt line) and reserves `rtos-framebuffer-memory@93500000 { reg = <0x00 0x93500000 0x00 0x08000000>; }`; its header says it "is compatible with AM62P Device Manager firmware labelled as dss_display_share.wkup-r5f0_0.release.strip.out".
- Processor SDK Display Cluster guide (https://software-dl.ti.com/processor-sdk-linux/esd/AM62PX/09_02_01_10/exports/docs/system/Demo_User_Guides/Display_Cluster_User_Guide.html): "AM62Px supports display sharing between A53 and MCU R5 cores." Hardware: "Microtips LVDS Panel". Kernel crash test: "echo c > /proc/sysrq-trigger" — R5 tell-tales keep displaying.
- Conclusion on DSI: TI's documented sharing examples are OLDI/LVDS on DSS0; the Linux DT properties are generic per-DSS-instance and DSI hangs off DSS1, but **no TI document showing display sharing on the DSI output (DSS1) was found**, and the MCU+ SDK DSS driver has no DSI support.

**Toradex DSI accessories.**
- "Toradex DSI Display Adapter" (https://developer.toradex.com/hardware/accessories/add-ons/dsi-display-adapter/; datasheet https://docs.toradex.com/116794-toradex_dsi_display_adapter_datasheet.pdf): a passive pass-through — it "pass[es] through MIPI DSI interface to FPC/FFC connector" (34-way FFC, DSI D0..D3 + clock, I2C_2_DSI SCL/SDA, +5V_SW_DSI backlight rail, "no backlight driver in-[cluded]"). No bridge chip on the adapter. (The separate "DSI to LVDS Adapter" uses TI SN65DSI84-Q1; the "DSI to HDMI Adapter" uses Lontium LT8912B — https://www.toradex.com/accessories/verdin-dsi-to-lvds-adapter, https://docs.toradex.com/109491-verdin-dsi-to-hdmi-adapter-v1.1_verdin-dsi-to-hdmi-adapter-datasheet.pdf.)
- "Capacitive Touch Display 7" DSI" = Riverdi **RVT70HSDNWCA0** (https://developer.toradex.com/hardware/accessories/displays/capacitive-touch-display-7inch-dsi/, datasheet https://docs.toradex.com/116214-riverdi-dsi-7-inch-display.pdf): 1024×600, IPS, "Quad-Lane MIPI DSI", on-board bridge "DRIVING IC ON THE BOARD: SN65DSI83ZXHR" (DSI→LVDS bridge on the display), touch "CTP Driver ILI2132A", TFT panel RVT70HSLNWCA0. Timings (datasheet p.15, DCLK units): Thd 1024; HSYNC period min/typ/max 1114/1344/1400; H blanking 90/320/376; VSYNC period 610/635/800; V blanking 10/85/200.
- Toradex overlay for Verdin AM62P (https://git.toradex.com/cgit/device-tree-overlays.git/plain/overlays/verdin-am62p_panel-cap-touch-7inch-dsi_overlay.dts?h=toradex_ti-linux-6.6.y): enables `&dphy_tx0`, `&dsi0`, `&dss1` (`/* DSS1-VP1: DSI Output */`), on `&main_i2c1` ("Verdin I2C_2_DSI") a `bridge@2c { compatible = "ti,sn65dsi83"; enable-gpios = <&main_gpio0 39> /* DSI_1_BKL_EN, SODIMM 21 */; data-lanes = <1 2 3 4>; }` and `touch@41 { compatible = "ilitek,ili2132"; interrupts = <38 IRQ_TYPE_EDGE_RISING> /* DSI_1_INT#, SODIMM 17 */; reset-gpios = <&main_gpio0 35> }`; backlight `pwms = <&epwm0 1 6666667 0>` ("Verdin PWM_3_DSI, SODIMM 19"); panel timings come from `display-rvt70hslnwca0_overlay.dtsi`. Other AM62P overlays present: `verdin-am62p_dsi-to-hdmi_overlay.dts` (lontium,lt8912b @0x48 on main_i2c0), `verdin-am62p_panel-cap-touch-10inch-dsi_overlay.dts`, `verdin-am62p_dsi-to-lvds_*`, `verdin-am62p_uart4-mcu_overlay.dts`.

## 3. Boot flow, DM R5F vs MCU R5F, remoteproc layout, A53 Zephyr from U-Boot

**Cores.** U-Boot doc: "One Device manager Cortex-R5F for system power and resource management, and one Cortex-R5F for Functional Safety or general-purpose usage." (https://github.com/u-boot/u-boot/blob/master/doc/board/ti/am62px_sk.rst). DT: DM R5F = `wkup_r5fss0_core0: r5f@78000000` (ATCM 0x78000000, BTCM 0x78100000, `ti,sci-proc-ids = <0x01 0xff>`, `firmware-name = "am62-wkup-r5f0_0-fw"`); MCU R5F = `mcu_r5fss0_core0: r5f@79000000` (ATCM 0x79000000 32 KiB, BTCM 0x79020000 32 KiB, `ti,sci-dev-id = <9>`, `ti,sci-proc-ids = <0x03 0xff>`, `resets = <&k3_reset 9 1>`, `firmware-name = "am62p-mcu-r5f0_0-fw"`, `ti,atcm-enable = <0>; ti,btcm-enable = <1>; ti,loczrama = <0>`) (MAINLINE k3-am62p-j722s-common-{wakeup,mcu}.dtsi). MCU IRAM0/IRAM1: 0x79100000/0x79140000, 256 KiB each (k3-am62p.dtsi cbass_mcu ranges). Verdin datasheet: "Tightly Coupled Memory R5F: 256kB".

**ROM / SBL.** U-Boot K3 doc (https://github.com/u-boot/u-boot/blob/master/doc/board/ti/k3.rst): "the first core started will be inside the Security Management Subsystem (SMS) which will secure the device and start a core in the wakeup domain to run the ROM code. ROM will then initialize the boot media needed to load the binaries packaged inside `tiboot3.bin`, including a 32bit U-Boot SPL, (called the wakeup SPL) … The wakeup SPL, running on a wakeup domain core, will initialize DDR … load … `tispl.bin` into DDR. Once loaded the wakeup SPL will start one of the 'big' application cores … TF-A … OP-TEE and the main domain's U-Boot SPL." AM62P = "Combined binary with a split firmware: (eg: AM62)". TI IPC doc: "The wakeup R5F firmware runs device manager software (SciServer) … integrated as part of tispl.bin binary and is started early in the boot process by u-boot R5 SPL right after DDR initialization." (https://software-dl.ti.com/processor-sdk-linux/esd/AM62PX/latest/exports/docs/linux/Foundational_Components_IPC62px.html). MCU+ SDK boot flow: "ROM also loads TIFS binary to TIFS Cortex M4 … In case of AM62PX EVM, the SBL loads the DM Firmware to DM R5F. … the SBL stage 2 will boot the cores in following order, 1st HSM 2nd MCU and 3rd A53." (https://software-dl.ti.com/mcu-plus-sdk/esd/AM62PX/latest/exports/docs/api_guide_am62px/developer_guides/bootflow.html). Verdin U-Boot: `verdin-am62p_r5_defconfig` / `verdin-am62p_a53_defconfig`, OP-TEE `PLATFORM=k3-am62px`, eMMC layout tiboot3.bin @0x0, tispl.bin @0x400, u-boot.img @0x1400 (sectors) (https://github.com/u-boot/u-boot/blob/master/doc/board/toradex/verdin-am62p.rst).

**How the MCU R5F firmware is normally loaded (Linux SDK).** "In normal operation, the boot loader (U-Boot/SPL) boots and loads the A53 with the HLOS. The A53 then boots the R5F core." remoteproc looks for `am62p-mcu-r5f0_0-fw` for `79000000.r5f` (remoteproc0; `78000000.r5f` is remoteproc1); sysfs `echo stop/start > /sys/class/remoteproc/remoteproc0/state`; symlink default `/usr/lib/firmware/ti-ipc/am62pxx/ipc_echo_test_mcu2_0_release_strip.xer5f` (IPC doc above). U-Boot-side early loading ("rproc") for AM62P: the TI U-Boot page has a "3.1.2.8. RemoteProc" section but its body could not be extracted — **NOT VERIFIED** for AM62P; the Zephyr Verdin AM62 (M4) doc shows the generic K3 sequence `rproc init; rproc list; load mmc 0:2 ${loadaddr} /lib/firmware/…; rproc load ${loadaddr} 0 0x${filesize}; rproc start 0` (https://docs.zephyrproject.org/latest/boards/toradex/verdin_am62/doc/index.html). Toradex ships `verdin-am62p_uart4-mcu_overlay.dts` ("Verdin AM62P Cortex-R5F debug UART": `&mcu_uart0 { status = "reserved"; }`).

**Reserved memory for mcu_r5fss0_core0.** Mainline `k3-am62p-ti-ipc-firmware.dtsi` (included by k3-am62p-verdin.dtsi and used by k3-am62p5-sk.dts) and TDX k3-am62p-verdin.dtsi:
```
mcu_r5fss0_core0_dma_memory_region: memory@9b800000 { compatible = "shared-dma-pool"; reg = <0x00 0x9b800000 0x00 0x100000>; no-map; };   /* 1 MiB vrings */
mcu_r5fss0_core0_memory_region:     memory@9b900000 { compatible = "shared-dma-pool"; reg = <0x00 0x9b900000 0x00 0xf00000>; no-map; };   /* 15 MiB code/data */
wkup_r5fss0_core0_dma_memory_region: memory@9c800000 { reg = <0x00 0x9c800000 0x00 0x100000>; }
wkup_r5fss0_core0_memory_region:     memory@9c900000 { reg = <0x00 0x9c900000 0x00 0x01e00000>; }   /* 30 MiB (SK dts in mainline: 0xf00000) */
secure_tfa_ddr: tfa@9e780000   { reg = <0x00 0x9e780000 0x00 0x80000>; }
secure_ddr:     optee@9e800000 { reg = <0x00 0x9e800000 0x00 0x01800000>; }
&mcu_r5fss0_core0 { mboxes = <&mailbox0_cluster1 &mbox_mcu_r5_0>; memory-region = <&mcu_r5fss0_core0_dma_memory_region>, <&mcu_r5fss0_core0_memory_region>; memory-region-names = "dma", "firmware"; }
```
TI SK (TIK) additionally has `rtos_ipc_memory_region: rtos-ipc-memory@9b500000 { reg = <0x00 0x9b500000 0x00 0x00300000>; }` and `linux,cma size 0x24000000`. TI note: "The resource table entity … needs to be at the beginning of the remote processor external memory section."

**A53 Zephyr from U-Boot.** Zephyr sk_am62 doc (https://docs.zephyrproject.org/latest/boards/ti/sk_am62/doc/index.html): copy `zephyr.bin` to the first FAT partition, then at U-Boot: `fatload mmc 1:1 0x82000000 zephyr.bin; go 0x82000000` — i.e. Zephyr docs use `go` with a raw binary, **not `booti`**. Board DT (https://github.com/zephyrproject-rtos/zephyr/blob/main/boards/ti/sk_am62/sk_am62_am6254_a53.dts): `tfa_memory: memory@80000000 { reg = <0x80000000 DT_SIZE_M(32)>; } /* Reserved memory for TFA/OP-TEE */`, `a53_ddr_section: memory@82000000 { reg = <0x82000000 (DT_SIZE_G(2) - DT_SIZE_M(32))>; }`, `zephyr,console = &main_uart0`, `ipc0 { compatible = "zephyr,mbox-ipm"; mboxes = <&mbox0 1>, <&mbox0 0>; }` (mbox0 = mailbox cluster0 @0x29000000, `usr-id = <0>`, GIC_SPI 76). No Zephyr doc mentioning `booti` for AM62 was found.

## 4. Verdin AM62P specifics (k3-am62p-verdin.dtsi / -dahlia.dtsi)

Mainline and Toradex (toradex_ti-linux-6.6.y) versions agree on the following (MAINLINE k3-am62p-verdin.dtsi is Copyright 2025 Toradex; TDX copy is 1486 lines and additionally includes the mailbox/r5 nodes inline).
- aliases: `serial0 = &main_uart1; serial1 = &wkup_uart0; serial2 = &main_uart0; serial3 = &mcu_uart0; serial4 = &main_uart6; mmc0 = &sdhci0; mmc1 = &sdhci1; mmc2 = &sdhci2;` — `chosen { stdout-path = "serial2:115200n8"; }`.
- Debug console: `/* Verdin UART_3, used as the Linux console */ &main_uart0 { status = "okay"; }` (dahlia.dtsi). main_uart0 = `serial@2800000`, GIC_SPI 178 (k3-am62p-j722s-common-main.dtsi). Verdin datasheet pin table: SODIMM 147/149 UART_3_RXD/TXD = UART0_RXD/TXD.
- MCU domain UART: `/* Verdin UART_4 */ &mcu_uart0 { status = "okay"; }` (dahlia.dtsi); `mcu_uart0: serial@4a00000 { compatible = "ti,am64-uart", "ti,am654-uart"; reg = <0x00 0x04a00000 0x00 0x100>; interrupts = <GIC_SPI 185 …>; power-domains = <&k3_pds 149 …>; clocks = <&k3_clks 149 0>; }`. Datasheet: SODIMM 151/153 UART_4_RXD/TXD = MCU_UART0_RXD/TXD; SODIMM 61/63 (HDMI_1_HPD/CEC) are MCU_UART0_CTSn/RTSn ("HDMI not supported on Verdin AM62P"). UART_1 = main_uart1 (RTS/CTS), UART_2 = wkup_uart0.
- SD card: `/* Verdin SD_1 */ &sdhci1 { pinctrl-0 = <&pinctrl_sdhci1>, <&pinctrl_sd1_cd>; cd-gpios = <&main_gpio1 48 GPIO_ACTIVE_LOW>; disable-wp; vmmc-supply = <&reg_sd1_vmmc>; vqmmc-supply = <&reg_sd1_vqmmc>; ti,fails-without-test-cd; }` enabled in dahlia.dtsi; `sdhci1: mmc@fa00000 { compatible = "ti,am62-sdhci"; reg = <0x00 0x0fa00000 0x00 0x1000>, <0x00 0x0fa08000 0x00 0x400>; interrupts = <GIC_SPI 83 …>; power-domains = <&k3_pds 58>; bus-width = <4>; }`. eMMC = sdhci0 @0x0fa10000 (GIC_SPI 133, 8-bit, `non-removable`). Pins: MMC1_CMD 0x023c, CLK 0x0234, DAT0..3 0x0230/0x022c/0x0228/0x0224 (`AM62PX_IOPAD`).
- Mailbox nodes for R5F (mainline via k3-am62p-ti-ipc-firmware.dtsi; TDX inline): `&mailbox0_cluster0 { mbox_r5_0: mbox-r5-0 { ti,mbox-rx = <0 0 0>; ti,mbox-tx = <1 0 0>; } }` used by `wkup_r5fss0_core0` (mainline; TDX has no mboxes on the wkup core), and `&mailbox0_cluster1 { mbox_mcu_r5_0: mbox-mcu-r5-0 { ti,mbox-rx = <0 0 0>; ti,mbox-tx = <1 0 0>; } }` used by `mcu_r5fss0_core0`. MCU_UART0 pins: `pinctrl_mcu_uart0: mcu-uart0-default-pins { AM62PX_MCU_IOPAD(0x0014, PIN_INPUT, 0) /* (B6) MCU_UART0_RXD */ /* SODIMM 151 */ AM62PX_MCU_IOPAD(0x0018, PIN_OUTPUT, 0) /* (C8) MCU_UART0_TXD */ /* SODIMM 153 */ }` (i.e. PADCFG 0x04084014 / 0x04084018, mux mode 0).
- RAM: `memory@80000000 { /* 2G RAM */ reg = <0x00000000 0x80000000 0x00000000 0x80000000>; device_type = "memory"; }` → DDR starts at 0x80000000, 2 GiB. Datasheet: "RAM Capacity 2GB, LPDDR4, 32-bit single rank, 3733MT/s"; SoC "AM62P54CVMHIAMHR"; variants on the product page: 00991000 V1.0A, 00991001 "Verdin AM62P Quad 2GB WB IT V1.0B (Q4 2025)", 00991100 V1.1A (https://developer.toradex.com/hardware/verdin-som-family/modules/verdin-am62p/).
- Display-related pins in the Verdin dtsi: `pinctrl_dsi1_int` (main_gpio0 38, DSI_1_INT#), `pinctrl_dsi1_bkl_en` (main_gpio0 39, DSI_1_BKL_EN), `pinctrl_pwm3_dsi_gpio` (main_gpio1 16), I2C_2_DSI = main_i2c1. No dss/dsi node is enabled in the base dtsi (only in overlays, §2).

## 7. Slint no_std / software renderer

- Slint MCU guide (https://github.com/slint-ui/slint/blob/master/api/rs/slint/mcu.md; rendered at https://docs.slint.dev/latest/docs/rust/slint/docs/mcu/): `cargo add slint@1.16 --no-default-features --features "compat-1-2 unsafe-single-threaded libm renderer-software"`; "Slint requires a global memory allocator in a bare metal environment with `#![no_std]`."; `unsafe-single-threaded`: "changes Slint to use unsafe static for storage. This way, you guarantee to use Slint API only from a single thread, and not from interrupt handlers."; `libm`: "provide traits and functions for floating point arithmetic … not available in bare metal"; `renderer-software`: built-in software renderer. Platform trait needs `create_window_adapter()` and `duration_since_start()`; rendering via `SoftwareRenderer::render()` (full frame buffer) or `render_by_line()` (line buffer). The MCU doc contains **no** mention of nightly vs stable or of aarch64 targets (examples are thumbv6m/thumbv7em/thumbv8m and Xtensa ESP32).
- Cargo features (https://github.com/slint-ui/slint/blob/master/api/rs/slint/Cargo.toml): `std`, `libm`, `unsafe-single-threaded`, `renderer-software`, and `software-renderer-path = ["i-slint-renderer-software/path"]` — "implicitly enabled by the `std` feature, but can be enabled without `std` if you want to use the software renderer in a `#![no_std]` environment and need support for Path elements."
- MSRV (https://github.com/slint-ui/slint/blob/master/CHANGELOG.md): 1.9.0 → Rust 1.77; 1.10.0 → 1.82; 1.13.0 → 1.85; 1.14.0 → 1.88; 1.17.0 → 1.92. Workspace `Cargo.toml` on master: `rust-version = "1.92"`, `version = "1.18.0"`. These are stable-toolchain versions; no nightly requirement is stated anywhere in the fetched docs.
