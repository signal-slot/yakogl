Method. The seven round-3 images and T14aa were built with DEQP_MODULE=gles3 tools/cts/pi4-deqp-images.sh <cut pi4-gles3-tree.txt> <dir> <labels> from a checkout of b1b5b845 and the gles3 stage 1 of recipe section 2 built from it on this worker (cts-build-zephyr: libraries in <WORK>/build, 453 ninja steps); each built rc=0 build=b1b5b845 with the check-deqp-images conformance line, T14aa at RAM 178,236 KB (67.99 %) with texture-2048.conf. The leased serial console holds the Pi 4's one-client UART bridge, so tools/board.sh pi4's steps were done by hand in its order, one image at a time, T14aa alone first: prechecks over ssh (no staged image, no tryboot.txt backup, no config-linux.txt, twice the image free on /boot/firmware), the stock tryboot.txt (one newline) backed up and read back by sha256, the image installed as /boot/firmware/yakogl-<LABEL>.bin with pi4_config's tryboot.txt lines, both read back, sudo reboot "0 tryboot", the console read up to the end line, Linux back (a new boot id), the image removed and the stock tryboot.txt put back, compared, the backup removed and read back (cycles.txt). Each console file holds the bytes from the firmware's first line to the image's end line, CRs and NULs dropped; for this session's eight consoles the byte count with the CRs restored was checked equal to the serial range it came from, before tools/cts/console-redact.py (the redaction pass of recipe section 6) rewrote the dEQP release number of the banner line in every console of the record. 0 GPU recoveries, 0 job timeouts, 0 hung jobs, 0 MMU faults, 0 resets before the end (tools/cts/pi4-console-scan.py; its 'faults 1' per image is the refused case's ResourceError); Linux was back 294-303 s after each reboot in this session, 296-311 s in the first attempt.
