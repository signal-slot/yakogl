Method. A worktree of `b1b5b845` (`git describe`: `b1b5b845`); VK-GL-CTS 93bca01 with its externals (`tools/cts/deps-env.sh --build`'s fetch, so the consoles' `dEQP Core` line carries the tag-derived version string); the gles3 stage 1 of `docs/es3/board-recipe-pi4.md` section 2 (Zephyr SDK 1.0.1, 4 cores, 453 ninja steps) built from that worktree; then `DEQP_MODULE=gles3 tools/cts/pi4-deqp-images.sh <current pi4-gles3-tree.txt> <dir> S32c1 S32c2 S32c3 S32c4` run from the worktree, with the case lists of the current table (the `b1b5b845` table has no S32c1-S32c4): four `rc=0 build=b1b5b845` lines, each `.config` passed by `check-deqp-images.py --config --gles3`, each image `RAM: 161844 KB 256 MB 61.74%`. The board runner could not capture the console: the Pi 4's UART bridge takes one client at a time and the leased serial console held it. As in the other `b1b5b845` sessions, `tools/board.sh pi4`'s steps were done by hand in its order, one image at a time (one GL client on the board at a time): free-space and leftover prechecks over ssh, the image installed to `/boot/firmware/yakogl-<LABEL>.bin` and `tryboot.txt` written with `pi4_config`'s lines (`[all]`, `kernel=`, `arm_64bit=1`, `enable_uart=1`, `uart_2ndstage=1`; no `hdmi_timings`), both read back by sha256 before the reboot; `sudo reboot "0 tryboot"`; the console read through the leased serial console up to the end line; Linux back (a new boot id); the staged image removed and `tryboot.txt` put back to its previous one-newline content, read back. `config.txt` was not touched. Each console file holds the bytes the console received from the firmware's first line to the end line, CRs and the leading NUL dropped; the byte count of each body matched the serial span of its run.
