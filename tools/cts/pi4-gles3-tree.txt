# The whole dEQP-GLES3 mustpass for the Raspberry Pi 4 (driver/samples/zephyr/v3d_deqp
# built with DEQP_MODULE=gles3) in 91 images, one CONFIG_DEQP_CASE per line, the format
# of pi4-full-tree.txt: each line is preceded by "# image <LABEL>: <mustpass names it
# selects>", the label tools/board.sh pi4 tree names the record by; blank lines and '#'
# lines are skipped. Every one of the 42,810 names of gles3-mustpass.txt is selected by
# exactly one line (tools/cts/check-gles3-tree.py pi4-gles3-tree.txt proves it and pins
# each "# image" count; check-deqp-images.py runs it). The filters match dEQP's whole
# tree; the tally (deqp-uart-tally.py --mustpass tools/cts/gles3-mustpass.txt) restricts
# to the list. No image needs texture-2048.conf.
#
# Sized for the image's watchdog window, CONFIG_V3D_DEQP_LIFETIME_S 240 s less
# CONFIG_V3D_DEQP_PHOTO_S 30 s: a run has about 200 s after boot. The Pi 4's GLES2
# sweep (RESULTS.md "Pi 4: sweep 30") ran 25-60 ms per case, 2,949 shaders.operator
# cases in 111 s, and about 1.2 s per failing random shader; the AM62P's GLES3 run
# (RESULTS.md 1r, a 600 s window) outlived it on its texture line and ran
# texture.filtering.3d as named lists of 22. So: shader groups up to about 1,200 names
# an image, fragment_ops / ubo / uniform_api / state_query up to about 1,000, fbo /
# fragment_out / texture / buffer up to about 700, texture.filtering.* one subgroup
# each, texture.filtering.3d as named lists of at most 15, builtin_functions.precision
# about 200 (each case checks 16k sampled inputs against a CPU reference), lifetime.*
# alone (its init dies without transform feedback, RESULTS.md 1r, and would end the
# image's run), random.all_features by stage as in pi4-full-tree.txt. Every record
# prints "<n> cases in <ms> ms": an image near 200 s is split before the next sweep.
#
# Build: DEQP_MODULE=gles3 tools/cts/pi4-deqp-images.sh tools/cts/pi4-gles3-tree.txt <img-dir>
# Run, tally: docs/es3/board-recipe-pi4.md.
