# Texture sampling on the hand-written Zephyr GPU driver — DDK 25.2 analysis

BVNC 36.53.104.796 (BXS-4-64). DDK tree:
`scratchpad/ti-img-rogue-driver-25.2/`. Note this GPU uses the DDK's **`rogue/`**
codepaths (the instrumentation and our copied shaders come from
`services/server/devices/rogue/`), even though the config also lives under `hwdefs/volcanic/`.

Analysis only — no files were modified.

---

## TL;DR

- The `SAFEUI_DDK` capture hook is in **`PVRSRVRGXKickTA3DKM`** only
  (`services/server/devices/rogue/rgxta3d.c`). The TQ / blit path
  (`rgx_blit_test`) goes through a **completely different, un-instrumented**
  function, **`PVRSRVRGXSubmitTransferKM`** (`rgxtransfer.c`), which never calls
  KickTA3D. **Running `rgx_blit_test` today produces ZERO `SAFEUI_DDK` dumps.**
- On Volcanic/Rogue the TQ **3D blit** *is* a genuine textured 3D-core draw (real
  USC fragment shader doing a TPU `SMP`, real texture/sampler state, real PDS) —
  so it *would* be a representative oracle **semantically**. BUT the entire FW
  command (VDM/PPP/PDS/USC/texture-state) is assembled in **userspace** and handed
  to the KM as an **opaque byte blob** (`papaui8FWCommand`). The KM has no
  structured view of it, and the current hook does not dump it.
- **This is a kernel-mode-only DDK tree.** It contains **none** of the pieces you
  need to author a texture draw by hand: no TPU image-state packer, no
  sampler-state packer, no USC `SMP` instruction encoder, no PPP `TA_STATE`
  (`SIZEINFO*`) field defs. Those all live in the closed UM driver / the PCO
  compiler (Mesa). The KM only ever sees pre-baked bytes or a pre-built binary
  shader file.

---

## Q1 — Instrumentation hook location, and does TQ flow through it?

**Instrumented function: `PVRSRVRGXKickTA3DKM`**, in
`services/server/devices/rogue/rgxta3d.c`. The dumps are:

- GEOM (TA) kick command: `rgxta3d.c:4211` block, `PVR_LOG("SAFEUI_DDK GEOMKICK...")`
  at `rgxta3d.c:4219`, dwords at `:4232`; VDM-stream follow at `:4269`.
- 3D/FRAG kick command: `rgxta3d.c:4303` block, `SAFEUI_DDK FRAGKICK` at
  `:4311`, `FRAGCMD[...]` at `:4314`, then a one-shot follow of PDS/USC VAs in
  the frag command (`:4325+`, comment at `:4353` about the frag PDS `DOUTD`ing the
  coefficient buffer into the USC).
- All the supporting dumps (HWRT tiling `:2149`, freelist `:966`/`:2526`, PM
  handshake `:5846`/`:5991`, PTE walk `:441`, VHeap/MList `:474`) are in the same
  file and are all reached only from the TA3D kick path.

Helper plumbing the dumps use: `rgxmem.c:910/926/944`, `mmu_common.c:5071`,
`rgxfwcmnctx.c:565`, `osfunc.c:1398` — all read client device memory through the
server MMU context. None of these is a submit path of its own.

**The transfer/blit path is separate and NOT instrumented.**
`rgx_blit_test` → `PVRSRVRGXSubmitTransferKM` (`rgxtransfer.c:556`). Evidence it
is a distinct path with no `SAFEUI_DDK` and no KickTA3D call:

- `grep SAFEUI_DDK rgxtransfer.c` → nothing.
- `grep KickTA3D rgxtransfer.c` → nothing.
- It builds the CCB command with `RGXCmdHelperInitCmdCCB` (`rgxtransfer.c:1447`)
  and schedules via `RGXScheduleCommand(..., RGXFWIF_DM_3D, ...)`
  (`rgxtransfer.c:1561`) for 3D blits, or `RGXFWIF_DM_2D` (`:1632`) for the TLA/2D
  path. Contexts are created as `REQ_TYPE_TQ_3D`/`RGXFWIF_DM_3D` (`:191`) and
  `REQ_TYPE_TQ_2D`/`RGXFWIF_DM_2D` (`:248`).
- Crucially, `PVRSRVRGXSubmitTransferKM`'s signature takes
  `IMG_UINT32 *paui32FWCommandSize, IMG_UINT8 **papaui8FWCommand`
  (`rgxtransfer.c:565-566`): the **firmware command is pre-built in userspace and
  passed in as opaque bytes**. The KM only appends sync/fence handling and copies
  the blob into the CCB.

**Answer:** `rgx_blit_test` would produce **no `SAFEUI_DDK` output at all** with
the KM as instrumented today. CDM (`RGXKickCDM`) is a third, also-un-instrumented
path (compute); not relevant here.

## Q2 — Is TQ a usable oracle for a 3D-FS texture sample?

**Semantically: YES — a TQ 3D blit is a real textured 3D draw.**
The transfer queue on this HW runs blits on the **3D core** (`RGXFWIF_DM_3D`,
`rgxtransfer.c:191,1561`) using **real USC fragment shaders that sample the source
surface via the TPU**, driven by real PDS + texture/sampler state. This is what
the "TQ shader factory" produces:

- `services/include/rgxtransfer_shader.h` describes the **binary TQ shader file**
  ("info about TQ binary shader file generated by the TQ shader factory ... used by
  services UM when constructing blits using the shaders"). Struct
  `RGX_SHADER_HEADER` = `{ui32Version, ui32NumFragment, ui32SizeFragment,
  ui32SizeClientMem}`.
- `services/server/devices/rgxshader.c` (`PVRSRVTQLoadShaders`, `:125`) loads a
  per-BVNC file `RGX_SH_FILENAME "." <B.V.N.C>` (`:110/:117`) via `OSLoadFirmware`.
  The blob is split into a **client-mem region** (`RGXShaderCLIMem`, holds PDS +
  texture/sampler state templates) and a **USC-code region** (`RGXShaderUSCMem`,
  `:89-95`). So a working sample FS + its texture/PDS state genuinely exist on the
  board in `/lib/firmware/rgx.sh.36.53.104.796` (or `.36.V.104.796`).

**As a *capturable* oracle through the current KM: NO.**
The 3D blit command is assembled entirely in UM and reaches the KM as an opaque
`papaui8FWCommand` blob (Q1). The `SAFEUI_DDK` hook is on the TA3D kick, not on
`PVRSRVRGXSubmitTransferKM`, so nothing is dumped. To make TQ an oracle you would
have to **add new instrumentation** to `PVRSRVRGXSubmitTransferKM` that walks the
supplied blob the same way the TA3D hook walks its command — feasible but new work,
and the blob's internal layout (RGXFWIF_CMD_3D / VDM+PPP+PDS pointers) still has to
be decoded.

**Caveat on representativeness:** the TQ FS is a *minimal* fixed blit shader
(single texture, one SMP, passthrough to the output). That is actually *exactly*
what you want for "present a SW-rendered UI buffer as a texture" — but it is not a
general textured draw (no user varyings beyond the blit UV, canned sampler). Good
enough for the goal; not a template for arbitrary texturing.

## Q3 — Texture (image) state layout

**Not present in this KM tree.** The TPU image-state descriptor (the words a
shader's `SMP` consumes: base addr, width/height, stride, pixel format, swizzle,
twiddle/tiling mode) is packed by the **UM driver / PCO compiler**, not the KM.
Confirmations:

- No packer/def anywhere: `grep` for `TEXSTATE | IMAGE_STATE | TEXTURE_STATE |
  SMPSTATE | SAMPLERSTATE | TPUIMAGE | rgxtexstate | SetTextureState |
  WriteTexState | IMAGE_STATE_WORD` across the whole non-binary tree → **empty**.
- `hwdefs/volcanic/km/rgx_cr_defs_km.h` has only TPU **control CRs**
  (`RGX_CR_TPU_INDIRECT` `:104`, `RGX_CR_CLK_CTRL0_TPU_*` `:257+`), not the
  in-memory image-state format.
- `hwdefs/volcanic/rgxpmdefs.h` is Parameter-Management structs only (PB / freelist
  / MList / VHeap); no texture state.

What the tree *does* give you (the enums the UM packer keys off — useful when you
hand-build state):

- `include/public/powervr/buffer_attribs.h:34` `IMG_MEMLAYOUT`:
  `STRIDED`(0), `TWIDDLED`(1), `3DTWIDDLED`(2), `TILED`(3), `PAGETILED`(4),
  `INVNTWIDDLED`(5). **`IMG_MEMLAYOUT_STRIDED` is the linear, non-twiddled option**
  you want for a SW-rendered source buffer.
- Colourspace enum at `buffer_attribs.h:59` (`IMG_COLOURSPACE_FORMAT_LINEAR` etc.,
  a separate axis from memory layout).
- Pixel-format enum (`IMG_PIXFMT_*`) also lives in `powervr/` public headers.

**Bottom line:** the exact dword count and bit fields of the TPU image-state
descriptor for BVNC 36.53.104.796 are **not derivable from this tree**. Sources
for it: (a) Mesa's PCO/`pvr` driver (`pvr_tex_state` / `ROGUE_TEXSTATE_*`), or
(b) reverse it from a real capture — but see Recommended path, the TQ shader file
already contains a ready-made, correctly-packed descriptor template.

## Q4 — Sampler state layout

Same status as Q3: **not in this KM tree** (the same empty-grep evidence covers
`SAMPLERSTATE`/`SmpState`/`WriteSamplerState`). Sampler-state words (filter
nearest/linear, wrap/clamp addressing) are packed by UM/PCO. Get the field layout
from Mesa (`ROGUE_TEXSTATE_SAMPLER_*` / `pvr_sampler`) or lift the pre-packed
sampler words out of the TQ shader file's client-mem region (they encode
nearest-clamp for a 1:1 blit, or linear for scaled blits).

## Q5 — How texture+sampler state reaches the USC

The KM tree does not contain the PPP `TA_STATE` field defs either — `SIZEINFO1/2`
with `usc_varyingsize`/`pds_varyingsize`/`pds_texturestatesize`/`pds_tempsize`/
`usc_sharedsize`, and `TEXTUREDATABASE`/`TEXUNICODEBASE`, are **UM/USC-defs**, not
present here (`grep TEXTUREDATABASE|TEXUNICODE|pds_texture` → only comment strings
in `rgxta3d.c:335,387,4353`; no real defs). So this must be reconstructed from
Mesa/UM, but the mechanism (well established for Rogue/Volcanic) is:

1. A **PDS texture-state program** (built by UM) issues **`DOUTT`** loads that DMA
   the packed texture-image-state words + sampler-state words into the USC's
   texture-state store. This is a *separate* PDS program from the USC-code loader
   (**`DOUTU`**) and the varying/iterator loader (**`DOUTI`**/`DOUTD` for the
   coefficient buffer). Your current Gouraud path already uses `DOUTU` (USC exec
   offset, see the instrumentation comment at `rgxta3d.c:335,387`) and the frag
   `DOUTD` for the coefficient buffer (`rgxta3d.c:4353`); texturing **adds** a
   `DOUTT`-based texture-state program.
2. The **FS references a texture-state slot** implicitly: the USC `SMP` instruction
   carries a **texture-state index** and **sampler-state index** into the
   per-USC-instance state store that the PDS `DOUTT` populated (slot 0 for the
   first texture). No pointer is embedded in the FS; the slot ordering is the
   contract between the PDS texture-state program and the SMP operands.
3. In PPP `TA_STATE` you must set, in addition to what you already set:
   - `SIZEINFO1.pds_texturestatesize` (bits `[16:22]` per your notes) = number of
     dwords of PDS **texture-state program data** (was 0 for Gouraud) — nonzero.
   - the frag **`TEXTUREDATABASE`** / **`TEXUNICODEBASE`** words = base addresses
     of that PDS texture-state program's data / code segments.
   - `SIZEINFO2.usc_sharedsize` (`[23:31]`) usually grows: the packed texture +
     sampler state occupy USC **shared** registers, so the shared allocation must
     cover them.
   - `pds_tempsize`/`usc_varyingsize`/`pds_varyingsize` stay as-is except that the
     FS now consumes a **UV varying** (2 floats) instead of / in addition to the
     color varying, so the varying/coefficient sizes and the iterator (`DOUTI`)
     program change to describe a `vec2` UV (f32, and you likely want
     **perspective-correct** rather than the `f32_npc` you use for flat color).

Relate to your working fields: for Gouraud you have
`SIZEINFO1{usc_varyingsize[4:9], pds_varyingsize[10:15],
pds_texturestatesize[16:22]=0, pds_tempsize[0:3]}`,
`SIZEINFO2{usc_sharedsize[23:31]}`. For one texture the deltas are:
`pds_texturestatesize` becomes nonzero, add the `TEXTUREDATABASE/TEXUNICODEBASE`
words, bump `usc_sharedsize`, and adjust the varying set to carry UV.

## Q6 — The SMP USC instruction / any prebuilt sample binary

- **The USC `SMP` (sample) instruction encoding is NOT in this KM tree.** Nothing
  encodes or even names USC opcodes here (the only USC bytes present are the ones
  our instrumentation copied out of captures). The authoritative encoder is
  **Mesa's PCO compiler** (`src/imagination/` in mesa: the `SMP`/`smp2d`/`smp3d`
  ops, `ROGUE`/`PCO` ISA defs) — that is the right reference to hand-assemble a
  minimal "sample at UV, write RGBA to output" FS.
- **There IS effectively a prebuilt sample/blit USC binary on the board**, but not
  as a C array in this tree — it is the **TQ binary shader file** loaded by
  `rgxshader.c` (`PVRSRVTQLoadShaders`, `:125`; USC region via `RGXShaderUSCMem`
  `:89`). File name pattern `RGX_SH_FILENAME "." B.V.N.C` (`rgxshader.c:110`),
  i.e. on the Verdin it is `/lib/firmware/rgx.sh.36.53.104.796` (fallback
  `.36.V.104.796`). Its layout is `RGX_SHADER_HEADER` + per-fragment
  `{client-mem (PDS + tex/sampler state templates), USC code}`. **This blob is the
  fastest real oracle**: it contains a correctly-packed texture-state descriptor, a
  sampler-state descriptor, the PDS `DOUTT` texture-state program, and the USC
  `SMP` fragment shader — all for exactly this BVNC. You can parse it offline
  (header is trivial) without a running GPU.
- `firmware/volcanic/` contains only `tee_blobgen_{usc,pds,general}.c` (TEE blob
  generators for the *main* FW), **not** the TQ shader factory output — so the TQ
  `.sh` file must be taken from the board's `/lib/firmware`, not from this tree.

## Recommended minimal path

The single most useful artifact is the **on-board TQ binary shader file**
`/lib/firmware/rgx.sh.36.53.104.796`. It already contains, for this exact GPU, a
working blit = textured-quad pipeline: packed **texture image-state**, **sampler
state**, a **PDS `DOUTT` texture-state program**, and a **USC `SMP` fragment
shader**. Prefer this over trying to capture `rgx_blit_test` (which yields nothing
today) or hand-encoding SMP from scratch.

Concretely, shortest route to a textured quad on our carveout:

1. **Pull and parse the TQ shader file** from the board. Parse `RGX_SHADER_HEADER`
   (4 u32), then for each fragment split client-mem vs USC code exactly as
   `rgxshader.c` does (`RGXShaderCLIMemSize`/`RGXShaderUSCMemSize`/
   `RGXShaderCLIMem`/`RGXShaderUSCMem`, `:66-95`). This gives, byte-exact:
   a ready `ddk_sample_fs[]` (USC), the PDS texture-state program, and the
   texture+sampler state word templates.
2. **Reuse the templates, patch only addresses/dims.** Overwrite the image-state
   descriptor's base address → our carveout source buffer, width/height/stride →
   our UI buffer, memory layout → `IMG_MEMLAYOUT_STRIDED` (linear), format →
   our BGRA/RGBA8888. Leave the sampler state as-is (nearest-clamp) for 1:1
   presentation. Because the descriptor comes pre-packed for this BVNC, you avoid
   needing the (absent) field layout from Q3/Q4.
3. **What changes in our existing structures (vs the working Gouraud path):**
   - FS: swap `ddk_interp_fs[16]` → the extracted `SMP` blit FS.
   - Add a **new PDS texture-state program** (the `DOUTT` one from the blob) — this
     is the main new object; our current path has none.
   - PPP `TA_STATE`: set `SIZEINFO1.pds_texturestatesize` nonzero (from the blob),
     add `TEXTUREDATABASE`/`TEXUNICODEBASE` (point at the new PDS tex-state prog),
     bump `SIZEINFO2.usc_sharedsize` to cover the texture/sampler state.
   - Varyings: change the varying/`DOUTI` iterator + coefficient program from "one
     `vec4` color, f32_npc" to "one `vec2` UV" (perspective-correct); update
     `usc_varyingsize`/`pds_varyingsize` to match. VS: emit position + UV instead of
     position + color (our `ddk_vs[25]` copy likely needs the varying-write changed,
     or a second captured VS).
   - Geometry: full-screen quad (2 tris) with UV in [0,1]; the TA/tiling/PM setup,
     freelist, HWRT, and 3D-kick machinery are unchanged from the Gouraud path.
   - **New device memory** on the carveout: the source texture surface (our UI
     buffer, made GPU-visible), plus small allocations for the texture-state words,
     sampler-state words, and the PDS texture-state program.
4. **Only if step 1 is blocked** (file unreadable / factory-version mismatch,
   `RGX_TQ_SHADERS_VERSION` = 2, `rgxtransfer_shader.h:63`): fall back to adding
   `SAFEUI_DDK` instrumentation to `PVRSRVRGXSubmitTransferKM` that walks the
   `papaui8FWCommand` blob (decode RGXFWIF_CMD_3D → VDM/PPP/PDS/USC the same way the
   TA3D hook does), rebuild `pvrsrvkm.ko`, and run `rgx_blit_test` to capture a live
   textured draw. This is real new work but reuses the existing memory-walk helpers
   (`rgxmem.c:910`, `mmu_common.c:5071`).

Do **not** try to hand-assemble the USC `SMP` from the DDK — the encoding is not in
this tree; that route requires Mesa's PCO ISA and is strictly harder than lifting
the ready blit shader from the board's TQ shader file.
